Составное GitHub Action, которое готовит черновик следующего стабильного релиза `vX.Y.Z` по [Conventional Commits](https://www.conventionalcommits.org/), сделанным после последнего тега релиза, стабильного или предрелизного. Оно создаёт черновой релиз на GitHub или обновляет существующий и **никогда не публикует** его. Публикация черновика остаётся ручным шагом в интерфейсе GitHub.

Action запускает скрипт на Node.js без внешних зависимостей, поэтому не требует шага сборки и готового артефакта.

## Использование

Добавьте workflow в репозиторий, который использует Action:

```yaml
name: Release draft

on:
  push:
    branches: [main]
  workflow_dispatch:
    inputs:
      version:
        description: Optional stable X.Y.Z to use instead of the version derived from commits
        required: false
        type: string

permissions:
  contents: read

concurrency:
  group: release-draft
  cancel-in-progress: false

jobs:
  draft:
    permissions:
      contents: write
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0
          fetch-tags: true
          persist-credentials: false
      - uses: HagiCode-org/hagi-release-drafter@v1
        with:
          version: ${{ inputs.version }}
          title-template: 'Example v{version}'
```

Группа `concurrency` не даёт двум запускам одновременно создавать или редактировать черновик.

## Входные параметры

| Параметр | Обязательный | По умолчанию | Описание |
| --- | --- | --- | --- |
| `version` | Нет | `''` (вычисляется из коммитов) | Стабильная версия `X.Y.Z`, которая используется вместо вычисленной. Значения с ведущим `v` или с суффиксом предрелиза отклоняются. |
| `title-template` | Нет | `v{version}` | Заголовок релиза. `{version}` заменяется на `X.Y.Z` без префикса. Тег всегда `v{version}`. |
| `github-token` | Нет | `${{ github.token }}` | Токен для вызовов GitHub API. Вызывающий job должен выдать `contents: write`. |

## Выходные данные

| Выход | Пример | Описание |
| --- | --- | --- |
| `version` | `1.4.0` | Определённая стабильная версия без ведущего `v`. |
| `tag` | `v1.4.0` | Тег релиза. |
| `notes-file` | `/home/runner/work/_temp/release-notes.md` | Путь к отрендеренному телу релиза на раннере. |
| `release-url` | `https://github.com/owner/repo/releases/tag/v1.4.0` | URL созданного или обновлённого черновика. |

## Права доступа

- Job, который вызывает Action, нужен `contents: write`, чтобы создавать или редактировать черновик.
- Checkout нужен только `contents: read`.
- Action не требует права `pull-requests` и никаких других прав на запись.

## Требования к checkout

Версия и заметки вычисляются по полной истории git и её тегам. Выполняйте checkout с `fetch-depth: 0` и `fetch-tags: true`. Поверхностный checkout завершается сразу с сообщением, которое называет эти параметры, и не выдаёт молча `0.1.0`.

## Как выбирается версия

1. Основа — тег релиза с наивысшим приоритетом, достижимый из `HEAD`, при сортировке по SemVer 2.0. Теги
   предрелизов, например `v0.1.0-beta.97`, учитываются, `v0.1.0-beta.100` стоит выше `v0.1.0-beta.97`, а стабильный
   тег стоит выше собственного предрелиза. Теги, не подходящие под грамматику тегов релиза, игнорируются: метаданные
   сборки (`+`), ведущие нули и имена, не соответствующие semver, например `release-2`.
2. Версия вычисляется из основной части `X.Y.Z` базового тега. Несовместимое изменение увеличивает мажорную версию,
   а при мажорной версии `0` — минорную.
3. Коммит `feat` увеличивает минорную версию и сбрасывает патч в ноль.
4. Любой другой набор коммитов увеличивает патч.
5. Если из `HEAD` не достижим ни один тег релиза, версия равна `0.1.0`, а заметки охватывают всю историю.
6. Параметр `version` переопределяет вычисленную версию. Коммиты в заметках от этого не меняются.

Заметки всегда охватывают коммиты после базового тега и до конца диапазона. Конец — это `HEAD`, если только
`--end-tag` в CLI не завершает диапазон одного репозитория на теге релиза. `--start-tag` в CLI может закрепить базовый
тег одного репозитория, и это единственный способ выбрать другую основу.

**Ограниченные диапазоны.** Репозиторий с `--end-tag` берёт версию из основной части `X.Y.Z` конечного тега, а не из
правил увеличения версии, потому что его диапазон описывает уже существующий релиз. Например, `v0.1.0-beta.95` даёт
`0.1.0`. `--version` по-прежнему переопределяет её. Без `--end-tag` правила выше действуют без изменений.

**Изменение поведения:** Action и CLI используют это правило совместно. Репозиторий, среди достижимых тегов которого
есть предрелиз, теперь получает другой диапазон и другую версию, чем давали прежние релизы этого Action. Репозитории,
у которых все теги релизов стабильные, это не затрагивает.

## Conventional Commit: типы и разделы

Каждый коммит попадает в первый раздел, правило которого он соответствует. Пустые разделы опускаются, а коммиты сохраняют порядок git: от новых к старым.

| Раздел | Что попадает |
| --- | --- |
| Breaking Changes | Любой коммит с `!` после типа или области, а также коммит с футером `BREAKING CHANGE:` или `BREAKING-CHANGE:`. |
| Features | `feat` |
| Fixes | `fix` |
| Performance | `perf` |
| Documentation | `docs` |
| Maintenance | `build`, `ci`, `chore`, `refactor`, `revert`, `style`, `test` |
| Other Changes | Все остальные типы, включая заголовки, которые не соответствуют формату Conventional Commits. |

Каждая запись выводится как `- **scope:** description ([`short-sha`](commit-url))`. Префикс области опускается, если у коммита нет области.

### Как исключить коммит из заметок

Коммит, **тема** которого (строка заголовка) содержит `skip-release-notes`, исключается из заметок релиза. Совпадение
ищется как подстрока без учёта регистра, например `docs: reword intro (skip-release-notes)`. Маркер всегда включён; ни входной параметр,
ни флаг, ни настройка не включают и не отключают его. Проверяется только тема, поэтому тело или футер, в которых упомянута
эта фраза, коммит не скрывают.

Пропущенный коммит обрабатывается так, будто его нет в диапазоне:

- Он не выводится и не учитывается ни в лимите записей, ни в подвале `Showing N of M commits`, ни в поле JSON `commitCount`.
- Он не влияет на версию. Пропущенный `feat:` не вызывает увеличение минорной версии; версия вычисляется так, будто коммита нет.
- Если пропущены все коммиты диапазона, в заметках выводится `_No changes yet._`.

## Ограничение числа записей

Тело релиза выводит не более **100 записей коммитов**. Заголовки разделов, подвал и текст для пустого диапазона в лимит не входят. Если кандидатов-коммитов 100 или меньше, выводятся все коммиты.

Для каждого репозитория CLI сообщает, сколько есть кандидатов-коммитов и сколько записей выведено, поэтому усечённый список изменений никогда не остаётся незамеченным. Сам лимит не меняется.

Каждому кандидату присваивается уровень приоритета по типу Conventional Commit. Применяется первое подходящее правило.

| Уровень | Соответствие |
| --- | --- |
| 1 | Критические изменения любого типа и `feat` |
| 2 | `fix`, `perf` |
| 3 | `refactor`, `revert` и любой коммит с областью `security` (без учёта регистра). `fix(security)` остаётся на уровне 2. |
| 4 | `build`, `chore`, `ci`, `docs`, `style`, `test` и заголовки, не соответствующие формату Conventional Commits |

Если кандидатов больше 100, коммиты пропускаются, начиная с самого низкого уровня, пока не останется 100:

1. Уровень 4 раньше уровня 3, уровень 3 раньше уровня 2, уровень 2 раньше уровня 1.
2. Внутри уровня 1 `feat` пропускается раньше критических изменений.
3. Без области раньше, чем с областью.
4. Более старые раньше более новых.

Чтобы коммит `chore`, `ci` или `docs`, связанный с безопасностью, не попадал на уровень 4, укажите у него область `security`, например `chore(security): rotate signing key`.

Если какой-либо коммит пропущен, тело заканчивается подвалом вида `_Showing 100 of 170 commits._ [Full changelog](https://github.com/owner/repo/compare/v1.3.0...<sha>)`. Ссылка ведёт на сравнение от базового тега, который может быть стабильным или предрелизным, до `HEAD`, а если тега релиза нет, на список коммитов.

Лимит влияет только на выводимое тело. Версия по-прежнему вычисляется по всем кандидатам, включая пропущенные.

## Политика тегов

- Каждый релиз этого Action получает неизменяемый тег `vX.Y.Z`.
- Подвижный мажорный тег `v1` указывает на самый новый релиз `1.x.y`.
- Потребители закрепляют `@v1`, чтобы получать совместимые исправления. Для полной воспроизводимости закрепите точный `@vX.Y.Z`.

Создание этих тегов входит в процесс выпуска самого Action, а не в workflow потребителя.

## Что Action не делает

- Не публикует релиз. У него нет входов `publish` и `draft: false`, и он никогда не выполняет операцию, которая переводит черновик в опубликованное состояние.
- Не создаёт и не перемещает git-теги. Черновик указывает на коммит `HEAD`, полученный checkout.
- Не удаляет черновики. Если их несколько, он редактирует первый, который вернул GitHub, поэтому сопровождающий, который хранит несколько черновиков, должен чистить их вручную.

## Локальный предпросмотр через CLI

Тот же движок запускается на вашей машине как `hagi-release-drafter`, поэтому версию и заметки релиза можно
просмотреть до выпуска. CLI читает только историю git. Он никогда ничего не публикует, не обращается к GitHub API
и не требует токена. Он пишет только в stdout, stderr, файл `--output` и кэш URL.

### Запуск и установка

CLI требует Node.js 24 или новее и git. В клоне этого репозитория один раз соберите CLI:

```bash
pnpm install
pnpm run build
node dist/cli.js --help
```

Чтобы добавить команду в `PATH`, упакуйте пакет и установите tarball:

```bash
npm pack
npm install -g ./hagicode-hagi-release-drafter-0.1.0.tgz
hagi-release-drafter --help
```

### Подкоманды и входные данные репозитория

| Команда | Что выводит |
| --- | --- |
| `hagi-release-drafter version` | Следующую стабильную версию, например `1.4.0`. |
| `hagi-release-drafter notes` | Тело релиза. Для одного репозитория при выводе по умолчанию оно побайтово совпадает с файлом заметок Action. |

Без входных данных используется текущий каталог, если это рабочее дерево git. Иначе укажите один или несколько
входов: либо как `--repo <input>` (можно повторять), либо как позиционные аргументы. Вход — это локальный путь к
рабочему дереву git или HTTPS-URL `github.com`, с суффиксом `.git` или без него. Входы обрабатываются по
порядку, по одному репозиторию за раз.

```bash
# The current repository
hagi-release-drafter version
hagi-release-drafter notes

# Commit links when the repository has no github.com origin remote
hagi-release-drafter notes --github-repository HagiCode-org/hagi-release-drafter

# Several repositories in one report
hagi-release-drafter version ./repos/a ./repos/b
hagi-release-drafter notes --layout merged --repo ./repos/a --repo https://github.com/HagiCode-org/hagi-release-drafter

# Start one repository's range at a prerelease tag; the other keeps automatic selection
hagi-release-drafter version --start-tag ./repos/b=v0.1.0-beta.97 ./repos/a ./repos/b

# Notes for a release that is already cut: only the commits between two release tags
hagi-release-drafter notes --start-tag ./hagicode-core=v0.1.0-beta.94 --end-tag ./hagicode-core=v0.1.0-beta.95 ./hagicode-core

# JSON for other tools, written to a file
hagi-release-drafter notes --format json --output report.json ./repos/a ./repos/b

# An explicit version, for one repository only
hagi-release-drafter version --version 2.0.0 ./repos/a
```

### Флаги

| Флаг | Значение |
| --- | --- |
| `--repo <input>` | Вход-репозиторий. Можно повторять. |
| `--layout <name>` | `per-repo` (по умолчанию) или `merged`. Меняет только отчёт в Markdown. |
| `--format <name>` | `markdown` (по умолчанию) или `json`. |
| `--output <file>` | Записать результат в файл. Stdout остаётся пустым. |
| `--version <X.Y.Z>` | Использовать эту стабильную версию вместо вычисленной. Допускается только для одного репозитория. |
| `--github-repository <owner/name>` | Идентификатор для ссылок на коммиты. Применяется ко всем входам и переопределяет удалённый репозиторий `origin`. |
| `--start-tag <input>=<tag>` | Начать диапазон одного репозитория с этого тега релиза вместо самого нового. `<input>` должен в точности совпадать с репозиторием в том виде, как он указан, например `./web`, поэтому `web` и `./web` — разные входы. Тег должен существовать и быть достижимым из `HEAD` этого репозитория. Можно повторять, по одному на репозиторий. |
| `--end-tag <input>=<tag>` | Закончить диапазон одного репозитория на этом теге релиза, например `v0.1.0-beta.95`, вместо `HEAD`. Действуют те же правила, что и для `--start-tag`, и тег должен существовать и быть достижимым из `HEAD` этого репозитория. Без `--start-tag` началом служит самый новый тег релиза ниже конца. Тогда версия — это основная часть `X.Y.Z` тега, если не указан `--version`. Можно повторять, по одному на репозиторий. |
| `--cache-dir <dir>` | Корневой каталог кэша для клонов по URL. См. ниже. |
| `--fail-fast` | Остановиться после первого репозитория с ошибкой. |
| `-h`, `--help` | Показать справку по использованию. |

### Раскладки и форматы

- **`per-repo`** (по умолчанию) начинается со сводной таблицы: репозиторий, статус, версия, последний тег, число
  коммитов и число выведенных записей. Число коммитов — это все кандидаты-коммиты, а число выведенных записей — то, сколько записей
  показывают заметки. Затем каждый репозиторий получает блок `###`, разделы которого идут на уровне `####`. У репозитория
  с ошибкой версия пустая, а в блоке указана причина.
- **`merged`** даёт один раздел `## Changes`. Его разделы содержат записи всех успешно обработанных репозиториев,
  каждая с пометкой имени репозитория. Перед объединением каждый репозиторий сокращается до ста записей.
  Усечённый репозиторий получает строку вида `_hagicode-core: showing 100 of 1324 commits._` перед первым
  разделом.
- **`--format json`** выводит один объект с массивом `repositories` в порядке входов. Каждая строка содержит `input`,
  `name` и `status`. Успешные строки дополнительно содержат `version`, `lastTag`, `lastTagSource` (`pinned` или `auto`),
  `endTag` (конечный тег ограниченного диапазона, иначе `null`), `commitCount` (число кандидатов), `renderedCount` (записи в `notes`), `truncated` и `notes`.
  Строки с ошибкой дополнительно содержат `error`. JSON всегда использует форму по репозиториям, поэтому `--layout` на него не влияет.

### Коды завершения

| Код | Значение |
| --- | --- |
| `0` | Все репозитории обработаны успешно. |
| `1` | Хотя бы один репозиторий завершился ошибкой. Причина выводится в stderr и попадает в отчёт. Единственный репозиторий с ошибкой ничего не выводит в stdout. Отсутствующий или недостижимый `--start-tag` приводит к ошибке только своего репозитория. `--end-tag`, которого нет или который недостижим из `HEAD`, а также начальный тег, не являющийся предком своего конечного тега, тоже приводят к ошибке только своего репозитория. |
| `2` | Ошибка использования, ничего не вычислялось. Сюда входят неизвестная подкоманда или флаг, недопустимые версия, раскладка или формат, отклонённый вход, повторяющийся вход, `--version` с несколькими входами, а также некорректное, не относящееся к релизу, повторяющееся или неизвестное значение `--start-tag` или `--end-tag`. |

### Расположение кэша

Вход-URL клонируется с полной историей и всеми тегами в `<root>/repos/<owner>/<name>`. Корнем служит
`--cache-dir`, если он указан, иначе `$XDG_CACHE_HOME/hagi-release-drafter`, иначе
`~/.cache/hagi-release-drafter`. Последующие запуски подтягивают теги и историю в тот же клон. Ничего не удаляется
автоматически, поэтому чтобы освободить место, удалите каталог клона. Для приватных репозиториев используются уже имеющиеся у вас
учётные данные git. URL с именем пользователя или паролем отклоняется.

### Чего CLI не делает

- Он не публикует, не создаёт и не редактирует релиз и не обращается к GitHub API. Он не читает токен,
  а `GH_TOKEN` и `GITHUB_TOKEN` не оказывают никакого влияния.
- Он не изменяет ни один локальный репозиторий, который вы ему передали. Ссылки, теги и рабочее дерево остаются как были.
- Action не использует CLI. Он по-прежнему запускает `scripts/release-notes.ts` напрямую на Node.js 24, поэтому
  не требует шага сборки. Пакет npm содержит скомпилированный `dist/cli.js`, собранный из тех же исходников.

## Требования к раннеру

- Раннеры, которые хостит GitHub, включают `gh` и `git`. На self-hosted раннере установите GitHub CLI.
- Action сам устанавливает Node.js 24 через `actions/setup-node`.
